# 测试计划协议（g-forge 自身）

> 当用户请求"制定测试计划"、"补测试"、"测试覆盖"、"写回归测试"时，遵循本协议。

---

## 阶段 1：目标定义

**必做：**
1. 明确测试目标（功能验收 / 回归防护 / 性能基线 / 契约测试）
2. 找到被测功能的入口文件（`src/core/**`）
3. 查阅既有同类测试（`src/**/*.test.ts`）避免重复

**输出：** 本次补测的范围与不补的理由

## 阶段 2：测试分层设计

**必做：**
1. 列出单元测试范围（纯函数 / 模块级 API）
2. 列出集成测试范围（CLI 端到端、文件生成流程）
3. 标注每层预期的覆盖率目标

**原则：**
- 测试金字塔：单元 > 集成 > E2E
- 不盲目追求 100% 覆盖率

## 阶段 3：用例清单

**必做：**
1. 列出 Happy Path 用例
2. 列出边界用例（空输入 / 超大输入 / 特殊字符）
3. 列出异常用例（文件不存在 / 权限错误 / 网络失败）
4. 列出不变式（生成的模板能通过 validator）

**禁止：**
- 仅覆盖 happy path
- 用例命名含糊（如 `it('works', ...)`）

## 阶段 4：实现与运行

**必做：**
1. 按 Vitest 规范实现（与源文件同级 `*.test.ts`）
2. 每个用例独立可运行，无顺序依赖
3. Mock 边界清晰（仅 Mock fs / child_process 等外部依赖）
4. 运行 `pnpm test` 确认全部通过

## 阶段 5：评审

**必做：**
1. 输出覆盖率报告（`pnpm test --coverage` 如已启用）
2. 识别未覆盖的关键分支
3. 决定补测或显式标记为已知风险
