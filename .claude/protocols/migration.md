# 数据/Schema 迁移协议

> 当用户请求"数据迁移"、"Schema 变更"、"数据库变更"、"接口升级"、"破坏性变更"时，遵循本协议。

---

## 阶段 1：影响分析

**必做：**
1. 阅读 `docs/DATA_MODEL.md`（如存在）确认当前数据结构
2. 阅读 `docs/API.md`（如存在）确认受影响的接口
3. 分析变更的影响范围：
   - 哪些表/集合/文件被修改
   - 哪些 API 端点受影响
   - 是否有下游消费者
   - 数据量评估（影响迁移策略）
4. 判断变更类型：

| 类型 | 示例 | 风险等级 |
|------|------|----------|
| 向后兼容 | 新增可选字段 | 低 |
| 需迁移 | 字段重命名、类型变更 | 中 |
| 破坏性 | 删除字段、Schema 重构 | 高 |

**输出：**
- 变更类型和风险等级
- 影响范围评估
- 是否需要 ADR（高风险变更必须写 ADR）

**禁止：** 未完成影响分析就开始写迁移代码

## 阶段 2：迁移方案设计

**必做：**
1. 设计迁移策略：

   - **蓝绿切换**：新旧并存，验证后切换
   - **渐进迁移**：分批处理，支持暂停/回滚
   - **一次性迁移**：适用于小数据量、低风险场景

2. 编写迁移脚本/代码，包含：
   - 正向迁移（up）
   - 回滚迁移（down）
   - 数据校验（verify）
   - 幂等性保证（重复执行不报错）

3. 如涉及 API 变更，设计版本过渡：
   - 新旧 API 并存期（推荐）
   - 或一次性切换（需协调所有消费者）

**输出：**
- 迁移方案（等待用户确认）
- 迁移脚本结构
- 回滚方案

## 阶段 3：实现

**必做：**
1. 实现迁移脚本，确保幂等
2. 实现回滚脚本
3. 更新受影响的业务代码
4. 编写测试：
   - 迁移正向执行测试
   - 回滚测试
   - 业务代码兼容性测试
5. 遵循 `.claude/rules/` 中的所有规则

**禁止：**
- 没有回滚方案的迁移
- 跳过迁移测试

## 阶段 4：验证

**必做：**
1. `pnpm typecheck` — 类型检查通过
2. `pnpm test` — 全量测试通过
3. 迁移脚本干跑（dry-run）验证
4. 回滚脚本验证

**输出：**
- 迁移就绪报告
- 执行步骤（运维手册形式）

## 阶段 5：文档更新

**必做：**
1. 更新 `docs/DATA_MODEL.md`（如存在）
2. 更新 `docs/API.md`（如涉及 API 变更）
3. 高风险变更写入 ADR（`docs/decisions/`）
4. 如需运维操作，写入 `docs/runbooks/`

**完成标志：** 迁移脚本就绪 + 回滚方案验证 + 文档同步
