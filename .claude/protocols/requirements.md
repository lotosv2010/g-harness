# 需求梳理协议（g-harness 自身）

> 当用户请求"梳理需求"、"确认需求"、"对齐需求"、"需求评审"时，遵循本协议。

---

## 阶段 1：现状盘点

**必做：**
1. 阅读 `docs/SPEC.md`，确认产品边界与既有功能
2. 阅读 `docs/tasks/BOARD.md` 与 `CURRENT.md`，确认进行中/待办任务
3. 阅读相关 ADR（`docs/decisions/`）
4. 列出与新需求相关的已有模块/功能

**输出：**
- 现状摘要（已实现了什么、正在做什么、与新需求的关系）

## 阶段 2：需求解构

**必做：**
1. 用一句话复述需求意图
2. 拆解为可验证的子需求（FR-XX 列表）
3. 标注优先级 P0/P1/P2
4. 明确非功能约束
5. 显式列出所有**未定义**的输入/边界条件

**禁止：**
- 使用"更好"、"更快"、"更易用"等主观描述
- 所有验收标准必须可机器检查

## 阶段 3：澄清歧义

**必做：**
1. 针对未定义项逐条提问
2. 每个问题给出"假设答案"供用户快速确认
3. 必须等用户回答后再进入方案设计

## 阶段 4：需求契约

**必做：**
1. 输出 `FR-XX` 列表（ID + 标题 + 优先级 + 验收标准）
2. 输出 `NFR-XX` 约束（可度量指标）
3. 输出"本次不做"清单（显式声明范围外）
4. 等用户确认契约后方可进入设计

**输出形式：** 直接写入 `docs/SPEC.md` 相应小节，由用户评审。
