# 代码审查协议

> 当用户请求"审查"、"Review"、"检查代码"时，遵循本协议。
> 每个维度完成后，在回复中标记 `[✓ 维度N]`，Stop hook 会验证是否遗漏。

---

## 检查清单

### 维度 1：正确性
- [ ] 逻辑是否正确
- [ ] 边界条件是否处理
- [ ] 错误处理是否完善
- [ ] 类型是否准确

**完成标志：** `[✓ 维度1-正确性]`

### 维度 2：架构合规
- [ ] 是否遵循规则文件中的规则
- [ ] 模块边界是否正确
- [ ] 依赖方向是否合规
- [ ] 是否遵循既定模式

**完成标志：** `[✓ 维度2-架构]`

### 维度 3：代码质量
- [ ] 命名清晰且一致
- [ ] 函数单一职责
- [ ] 无重复代码
- [ ] 无不必要的复杂性

**完成标志：** `[✓ 维度3-质量]`

### 维度 4：测试覆盖
- [ ] 业务逻辑是否有测试
- [ ] 边界条件是否有测试
- [ ] 测试是否验证行为而非实现

**完成标志：** `[✓ 维度4-测试]`

### 维度 5：安全性
- [ ] 无硬编码密钥
- [ ] 用户输入已校验
- [ ] 无 XSS/注入风险
- [ ] 敏感数据已保护

**完成标志：** `[✓ 维度5-安全]`

### 维度 6：性能（按需）
- [ ] 无不必要的重渲染/重计算
- [ ] 无 N+1 查询
- [ ] 无大对象深拷贝
- [ ] 正确使用缓存

**完成标志：** `[✓ 维度6-性能]` 或 `[✓ 维度6-不涉及性能]`

## 输出格式

```markdown
## 审查结果：[通过 / 需修改 / 阻塞]

### 必须修复（Blocker）
- [ ] [文件:行号] 描述问题和建议

### 建议优化（Suggestion）
- [ ] [文件:行号] 描述建议

### 认可（Good）
- 值得肯定的做法
```

## 审查原则

- 关注正确性和架构，不纠结风格偏好
- 建议要具体可操作
- 区分"必须修复"和"建议优化"
- 认可做得好的地方
