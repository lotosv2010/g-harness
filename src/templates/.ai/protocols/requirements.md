# 需求梳理协议

> 当用户请求"梳理需求"、"确认需求"、"对齐需求"、"需求评审"时，遵循本协议。
> 每个阶段完成后，在回复中标记 `[✓ 阶段N]`，Stop hook 会验证是否遗漏。

---

## 检查清单

### 阶段 1：现状盘点
- [ ] 读 `docs/SPEC.md`，确认产品边界与既有功能
- [ ] 读 `docs/PROJECT_MAP.md` + `docs/FEATURES.md`，确认已实现范围
- [ ] 读相关 ADR（`docs/decisions/`），确认已有决策
- [ ] 列出与新需求相关的已有模块/功能

**完成标志：** `[✓ 阶段1-现状盘点]`

### 阶段 2：需求解构
- [ ] 复述需求意图（一句话回声）
- [ ] 拆解为可验证的子需求（FR 列表）
- [ ] 标注优先级（P0/P1/P2）
- [ ] 明确非功能约束（性能、安全、合规）
- [ ] 列出所有**未定义**的输入/边界条件

**完成标志：** `[✓ 阶段2-需求解构]`

**禁止：** 模糊陈述（"更好"、"更快"、"更易用"），必须量化为可验收指标

### 阶段 3：澄清歧义
- [ ] 针对未定义项逐条向用户提问
- [ ] 每个问题给出"假设答案"供用户快速确认
- [ ] 等用户回答后再进入方案设计

**完成标志：** `[✓ 阶段3-澄清]` 或 `[✓ 阶段3-无歧义]`

### 阶段 4：需求契约
- [ ] 输出 `FR-XX` 列表（ID + 标题 + 优先级 + 验收标准）
- [ ] 输出 `NFR-XX` 约束（可度量的指标）
- [ ] 输出"本次不做"清单（显式声明范围外）
- [ ] 等用户确认契约后方可进入设计阶段

**完成标志：** `[✓ 阶段4-契约]`

**原则：** 验收标准必须可执行（"返回 200 且 body.id 为 UUID"），禁止"符合预期"等主观描述
