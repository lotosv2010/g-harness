# 线上事故响应协议

> 当用户报告"线上问题"、"生产事故"、"紧急修复"、"hotfix"时，遵循本协议。
> 每个阶段完成后，在回复中标记 `[✓ 阶段N]`，Stop hook 会验证是否遗漏。

---

## 检查清单

### 阶段 1：止血
- [ ] 明确事故现象（报错信息、影响范围、触发条件）
- [ ] 检查最近变更（`git log --oneline -20`）
- [ ] 定位根因（代码 / 配置 / 依赖 / 环境）
- [ ] 提出最小修复方案（止血优先，重构延后）
- [ ] 评估是否需要回滚

**完成标志：** `[✓ 阶段1-止血]`

**禁止：** 未定位根因就开始修改代码；止血阶段做大范围重构

### 阶段 2：修复实现
- [ ] 按止血方案编码（最小变更原则）
- [ ] 遵循规则文件中的所有规则
- [ ] 同步编写回归测试（覆盖触发事故的场景）
- [ ] commit message 标注 `fix:` + 关联事故 ID

**完成标志：** `[✓ 阶段2-修复]`

**禁止：** 搭便车修改无关代码；跳过回归测试

### 阶段 3：验证
- [ ] 类型检查通过
- [ ] 全量测试通过
- [ ] 代码检查通过
- [ ] 手动复现确认修复有效

**完成标志：** `[✓ 阶段3-验证]`

### 阶段 4：复盘文档
- [ ] 创建事故报告（如有影响的事故）

```markdown
# 事故报告：[简要标题]

**时间**：YYYY-MM-DD HH:mm
**严重度**：P0/P1/P2
**影响范围**：[描述]

## 时间线
- HH:mm — 发现问题
- HH:mm — 定位根因
- HH:mm — 修复上线
- HH:mm — 确认恢复

## 根因
[详细说明]

## 修复措施
[代码变更说明]

## 预防措施
- [ ] [预防项 1]
- [ ] [预防项 2]
```

- [ ] 如根因暴露架构缺陷，记录为技术债

**完成标志：** `[✓ 阶段4-复盘]`
