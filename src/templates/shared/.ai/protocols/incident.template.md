# 线上事故响应协议 — {{project_name}}

> 当报告"线上问题"、"生产事故"、"紧急修复"、"hotfix"时，遵循本协议。

---

## 阶段 1：止血

**必做：**
1. 明确事故现象（报错信息、影响范围、触发条件）
2. 定位根因：
   - 阅读相关日志和错误堆栈
   - 检查最近变更（`git log --oneline -20`）
   - 确认是代码问题还是配置/依赖/环境问题
3. 提出最小修复方案（止血优先，重构延后）

**输出：**
- 根因分析（一句话）
- 影响范围评估
- 止血方案
- 是否需要回滚

**禁止：**
- 未定位根因就开始修改代码
- 止血阶段做大范围重构

## 阶段 2：修复实现

**必做：**
1. 按止血方案编码（最小变更原则）
2. 遵循项目规则文件中的所有约束
3. 同步编写回归测试（覆盖触发事故的场景）
4. 在 commit message 中标注 `fix:` + 关联的 issue/事故 ID

**禁止：**
- 搭便车修改无关代码
- 跳过回归测试

## 阶段 3：验证

**必做：**
1. 类型检查通过
2. 全量测试通过
3. lint 通过
4. 手动复现确认修复有效

**相关命令：**
{{commands}}

**输出：**
- 修复变更摘要
- 回归测试用例
- 验证结果

## 阶段 4：复盘文档

**必做（修复完成后）：**
1. 创建事故报告：

```markdown
# 事故报告：[简要标题]

**时间**：YYYY-MM-DD HH:mm
**严重度**：P0/P1/P2
**影响范围**：[描述]

## 时间线
- HH:mm — 发现问题
- HH:mm — 定位根因
- HH:mm — 修复上线
- HH:mm — 确认恢复

## 根因
[详细说明]

## 修复措施
[代码变更说明]

## 预防措施
- [ ] [预防项 1]
- [ ] [预防项 2]
```

2. 如果根因暴露了架构缺陷，记录为技术债

**完成标志：** 修复已验证 + 复盘文档已写入
