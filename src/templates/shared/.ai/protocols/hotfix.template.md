# 紧急修复协议 — {{project_name}}

> 绕过常规开发流程的快速修复通道，仅用于生产环境紧急问题。

---

## 触发条件

以下任一情况触发 hotfix 流程：
- 生产环境服务不可用或严重降级
- 用户数据安全受到威胁
- 核心业务流程阻断
- P0/P1 级别事故

## 1. 评估（≤5 分钟）

- 确认问题严重度：是否需要 hotfix 还是可走常规 bugfix
- 明确影响范围（用户数、功能模块、数据完整性）
- 判断是否需要立即回滚（见 `rollback` 协议）

## 2. 分支与修复

- 从 `main`（或当前发布 tag）创建 `hotfix/<描述>` 分支
- 最小化修改：只修复当前问题，禁止搭便车
- 修复代码必须包含回归测试
- commit 使用 `fix:` 前缀，标注事故 ID

## 3. 快速验证

- 跑核心测试套件（可跳过非关键慢测试）
- 类型检查必须通过
- 至少一人 review（紧急情况下可事后 review）

## 4. 发布

- 合并到 `main` 后立即发布
- 版本号使用 patch 递增
- 通知相关干系人修复已部署
- 确认监控指标恢复正常

## 5. 事后补全

- 将 hotfix 同步到开发分支（避免后续回归）
- 补写完整测试（如快速验证阶段跳过）
- 触发 `incident` 协议进行复盘
- 更新 `docs/runbooks/` 如发现新的操作手册需求

---

**注意：** hotfix 是例外流程，不可常态化使用。如频繁触发，需审视根因和质量门禁。
