# 回滚协议 — {{project_name}}

> 部署失败或发布后发现严重问题时的恢复流程。

---

## 触发条件

以下任一情况触发回滚：
- 部署后核心功能异常且无法快速修复（>15 分钟）
- 监控告警：错误率飙升、延迟剧增、服务不可用
- 数据一致性问题需要立即止损

## 1. 决策（≤5 分钟）

- **评估：** 问题是否可通过 hotfix 在 15 分钟内解决？
  - 是 → 走 `hotfix` 协议
  - 否 → 继续回滚流程
- **确认回滚目标版本：** 上一个稳定版本的 tag 或 commit SHA
- **通知：** 告知团队即将执行回滚

## 2. 执行回滚

### 2.1 应用回滚

```bash
# 方式一：Git revert（保留历史，推荐）
git revert <问题commit>..HEAD --no-commit
git commit -m "revert: rollback to <稳定版本>"

# 方式二：重新部署指定版本（CI/CD 触发）
# 在 CI 系统中选择上一个稳定的 release tag 重新部署
```

### 2.2 数据回滚（如涉及）

- 确认是否有 schema migration 需要回退
- 评估数据回滚的影响范围（丢失 vs 不一致）
- 执行 down migration 或从备份恢复

## 3. 验证

- 确认服务恢复正常（健康检查通过）
- 检查监控指标回到基线水平
- 抽样验证核心用户流程
- 确认无数据丢失或不一致

## 4. 善后

- 记录回滚时间线（发现 → 决策 → 执行 → 恢复）
- 分析根因：是代码问题、配置问题还是环境问题
- 修复问题后需在独立分支充分测试再重新发布
- 更新 `docs/runbooks/` 如需新增操作手册
- 考虑是否需要加强部署门禁（canary / 灰度比例）

---

**关键原则：**
- 止血优先于根因分析
- 保留完整审计日志
- 回滚是正常的工程操作，不是失败的标志
