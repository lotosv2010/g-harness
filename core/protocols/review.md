# 代码审查协议

> 当用户请求"审查"、"Review"、"检查代码"时，遵循本协议。

---

## 审查维度

按以下顺序逐一检查：

### 1. 正确性
- 逻辑是否正确
- 边界条件是否处理
- 错误处理是否完善
- 类型是否准确

### 2. 架构合规
- 是否遵循项目规则文件中的规则
- 模块边界是否正确
- 依赖方向是否合规
- 是否遵循既定模式

### 3. 代码质量
- 命名是否清晰且一致
- 函数是否单一职责
- 是否有重复代码
- 是否有不必要的复杂性

### 4. 测试覆盖
- 业务逻辑是否有测试
- 边界条件是否有测试
- 测试是否验证行为而非实现

### 5. 安全性
- 是否有硬编码密钥
- 用户输入是否校验
- 是否有 XSS/注入风险
- 敏感数据是否保护

### 6. 性能（按需）
- 是否有不必要的重渲染/重计算
- 是否有 N+1 查询
- 是否有大对象深拷贝
- 是否正确使用缓存

## 输出格式

```markdown
## 审查结果：[通过 / 需修改 / 阻塞]

### 必须修复（Blocker）
- [ ] [文件:行号] 描述问题和建议

### 建议优化（Suggestion）
- [ ] [文件:行号] 描述建议

### 认可（Good）
- 值得肯定的做法
```

## 审查原则

- 关注正确性和架构，不纠结风格偏好
- 建议要具体可操作（"建议改为 X" 而非 "这样不好"）
- 区分"必须修复"和"建议优化"
- 认可做得好的地方
